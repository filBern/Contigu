# QA du 2026-11-28 : événements, sauvegarde, rythme, Mult, Warden, textes

Passe sur le Core (réellement exécuté via .NET) et audit de lecture pour la Presentation (rien de visuel n'est vérifié en jeu : « d'après le code »). Aucun fichier du jeu ni des tests n'a été modifié ; les programmes de reproduction sont dans le scratchpad (hors dépôt).

## 1. Résumé

Exécuté :
- `dotnet test` : **670 réussis, 0 échec**.
- `content_audit.py` : 0 trouvaille (152 fertilizers lus par l'audit, 89 sprouts, 16 ennemis, 23 météos). `check_icon_tags.py` : 125 pastilles conformes. `glyph_audit.py` : « No missing glyphs » (après `pip install fonttools`, absent au départ).
- Fuzz avec invariants (`--check`) sur Classic, Marathon, Summer, Autumn, Orchard, Greenhouse : 100 parties `random` + 40 parties `planner` PLAN_DEPTH=2 `--endless` (graine 7), **avec `--events`** (sans cette option le bot n'ouvre jamais d'événement) : 0 `invariant:` / 0 `exception:`. `--each --runs 8` : « Every fertilizer and sprout played cleanly ».
- Équilibre planner profondeur 2, 400 parties, graine 1 : Spring 15,3 %, Winter 12,5 %, Summer 7,3 %, Autumn 16,0 %, Orchard 8,0 %, Greenhouse 6,8 %. Ces chiffres **reproduisent exactement** ceux de `CLAUDE.md`.
- Programmes jetables : (a) tous les événements x toutes les options x 0/1/4 fertilizers x Pollen 0/5/10/100 x 30 graines (invariants Pollen >= 0, sac >= 10, <= 4 fertilizers, cohérence `IsEventOptionAvailable`/`ResolveEvent`) ; (b) aller-retour du checkpoint de boutique (`CheckpointSnapshot` -> texte -> `Restore` -> texte) avec événement en attente, 6 défis x niveaux 1 et 4 x 6 graines x jusqu'à 14 manches, Endless inclus, puis résolution et sortie de boutique après reprise ; (c) sauvegardes altérées (identifiant inconnu, ancienne sauvegarde sans clés d'événement).

Verdict : le Core est solide sur les événements et la sauvegarde (aucun plantage, aucune incohérence d'état trouvée). Les problèmes réels sont : un ordre de calcul du Mult incohérent pour les +Mult de tuile, quelques écarts de texte/règle, et une documentation en retard sur le code.

Trouvailles : Bloquant 0 ; Majeur 1 ; Mineur 6 ; Clarté 8 ; Observation d'équilibre 3 ; incohérences de documentation 8 (section 3).

## 2. Trouvailles

### Majeur

**M1. L'ordre d'un +Mult de tuile par rapport aux fertilizers dépend de la place du fertilizer (slot 0 contre les autres)** (Confirmé)
- Où : `RunManager.TileUpgrades.cs:743-748` (`AddTileMult` n'étiquette pas `TriggeringModifierIndex`, donc 0 par défaut) ; `PlacementResult.cs:299` (tri par `TriggeringModifierIndex`, commentaire « deux événements de même index sont toujours le même modifier » : faux pour ces événements) ; reproduit côté affichage dans `GameBootstrap.Placement.cs:~730`.
- Repro (.NET, seed 3) : Keystone Sprout (+5 Mult) planté au centre d'un jardin vide, fertilizer Islet (x2, se déclenche sur une graine isolée) et Prism (inactif) en remplissage. Islet en slot 0 : `Mult = 1x2 + 5 = 7`. Islet en slot 1 : `Mult = (1+5)x2 = 12`. Événements : `ModifierMultiplier:2@0, MultBonus:5@0` contre `ModifierMultiplier:2@1, MultBonus:5@0`.
- Attendu : un ordre défini et documenté (le +Mult de tuile avant, ou après, tous les fertilizers). Obtenu : le +Mult de tuile est après le fertilizer du slot 0 mais avant les autres, et le résultat dépend de l'ordre d'émission en cas d'égalité (tri `List.Sort` non stable au-delà de 16 éléments).
- Impact : le score change du simple au presque double selon la place d'un fertilizer, sans que le joueur puisse le deviner. Touche tous les +Mult de tuile (Keystone et les autres `AddTileMult`).
- Piste : donner aux +Mult de tuile un index explicite (par exemple -1 pour « avant tous » ou `int.MaxValue` comme le Clean Sweep) et corriger le commentaire.

### Mineur

**m1. « Swap a fertilizer » peut rendre le fertilizer qu'on vient de perdre** (Confirmé)
- Où : `RunManager.Events.cs` (`Lose` puis `Grant` ; `GrantRandomModifier` tire parmi ce qui n'est plus tenu, donc aussi le fertilizer retiré à l'instant) ; `EventCatalog.cs` id 6, option 2.
- Repro : profil de déblocage « nouveau joueur » (`UnlockState(everythingAvailable:false)`, 32 fertilizers utilisables), 4 fertilizers tenus, événement 6, option 1, 2000 graines : **66/2000 (3,3 %)** donnent « You lose X. You gain X. » (avec toutes les cartes débloquées, environ 0,8 %).
- Impact : l'option « échange » ne fait rien ; texte absurde. Piste : exclure le fertilizer perdu du tirage.

**m2. Une option risquée reste proposée quand son effet principal est impossible, et la carte affiche une chance fausse** (Confirmé)
- Où : `RunManager.Events.cs:55-85` (la vérification ne porte que sur les options à issue unique) ; cartes concernées : « Taste the petals » et « Let the roots drink » (niveau de fertilizer) sans fertilizer, « Pick it » (Moonlit Greenhouse, 50 % « gain a random fertilizer ») et « Make a wish » (The Old Well) avec 4 fertilizers.
- Repro : programme (a). Exemples : 0 fertilizer, « Taste the petals » -> « You have nothing to grow. » ; 4 fertilizers, « Make a wish » -> « You lose 6 Pollen. Nothing grows for you this time. » : le joueur **paie 6 Pollen pour rien** (issue « lose 6 Pollen, gain a random fertilizer » à 33 %).
- Attendu : texte/probabilités conformes à ce qui peut arriver, ou option grisée (comme les options à issue unique). Impact : mise perdue sans le savoir. Piste : filtrer les issues impossibles avant de tirer (ou avant d'afficher les pourcentages).

**m3. Résultat « You lose 0 Pollen. » et « Next round: 1 fewer seeds. »** (Confirmé)
- Où : `RunManager.Events.cs:~127` (`"You lose " + (before - Lueur) + " Pollen."` sans cas 0) ; `Events.cs:~164` (pluriel fixe, alors que `Describe()` gère le singulier). Repro : événement 2 « Taste the petals », Pollen 0, graine 2 -> « You lose 0 Pollen. » ; « Sudden Rain / Collect the rainwater » -> « Next round: 1 fewer seeds. »
- Impact : texte maladroit. Piste : `Describe()` et le résultat devraient partager le même code de pluriel et omettre une perte de 0.

**m4. Niveau de difficulté 4 : « one seed less each round » n'enlève rien à la manche 1** (Confirmé)
- Où : `ChallengeDefinition.BudgetFor` (`roundIndex == 0` retourne `RunConfig.FirstRoundBudget` sans `PieceBudgetBonus`) ; texte `DifficultyLevels.cs:18`, `docs/PROGRESSION.md:13`.
- Repro (programme jetable) : `AtLevel(4).BudgetFor(0) = 20` pour les 6 défis, comme au niveau 1 ; `BudgetFor(1)` passe de 38 à 37 (Spring). Aussi : `PieceBudgetBonus` du défi (6 à 12 graines) est ignoré en manche 1, ce qui est probablement voulu mais n'est écrit nulle part.
- Piste : soit appliquer le malus du niveau à la manche 1, soit écrire « from round 2 » dans le texte.

**m5. Charger une sauvegarde de boutique contenant une amélioration retirée plante** (Confirmé avec un identifiant synthétique, Suspecté pour un cas réel)
- Où : `RunManager.Save.cs:FromSlotData` -> `UpgradeCatalog.Get` retourne null -> `ShopSlot.ForUpgrade` (`ShopSlot.cs:53`) NullReferenceException. Les fertilizers retirés sont gérés (`IsRetired`), pas les sprouts. Cas réel : `UpgradeId.TintedCells` (8) : `UpgradeCatalog.Get(TintedCells)` renvoie `null` (seul id de l'enum dans ce cas), et `ResumeSavedRun` (`GameBootstrap.RunFlow.cs:671`) n'entoure pas `Restore` d'un try.
- Repro : checkpoint de boutique dont `workshop=u,9999,-1;...` -> `RunManager.Restore` lève l'exception. Impact : « Continue » planté pour une sauvegarde ancienne ou d'une autre version (version de snapshot toujours 1). Piste : traiter une amélioration inconnue comme une case vide (comme `IsRetired`), et/ou `try/catch` autour de `Restore`.

**m6. Pollen affiché trop tôt pendant le décompte des graines inutilisées en fin de manche** (Suspecté, d'après le code)
- Où : `GameBootstrap.RunFlow.cs:117` (`displayedLueur = _run.Lueur - _run.LastRoundEndLueurBonus`) alors que `CompleteRoundSuccessfully` ajoute aussi `GrowModifiers()` (récoltes de fertilizers, 3 Pollen chacune) à `Lueur` sans l'inclure dans `LastRoundEndLueurBonus` (`RunManager.Combat.cs:214-216`).
- Attendu : le compteur ne montre pas la récolte avant le résumé. Obtenu : le compteur démarre déjà augmenté du Pollen des récoltes, puis `PlayShopHarvest` annonce « Harvest +N » après. Manquerait pour confirmer : Unity. Piste : soustraire aussi le Pollen de récolte.

### Clarté

- **C1. Options grisées sans explication** (Confirmé par le code) : `EventView.cs:~99` n'écrit « Needs N Pollen » que si le Pollen manque. Une option indisponible parce que le sac est trop petit (Burn it), qu'il n'y a aucun fertilizer à vendre/échanger (Sell/Swap) ou que les 4 emplacements sont pleins (Buy a cutting) est grisée sans raison affichée.
- **C2. « lose 3 seeds from your bag » ne dit pas que les graines sont tirées au hasard** (peuvent être des graines améliorées ou des Jokers) ; « Burn it » (id 5) peut détruire une graine à sprout. Le résultat ne nomme pas les graines perdues. De même « A Joker seed joins your bag » ne dit pas la forme (Joker tiré au hasard).
- **C3. Pourcentages tronqués** : `Describe()` utilise une division entière ; « Make a wish » affiche 33 % + 33 % + 33 % = 99 %. Deux issues de « Make a wish » (« lose 6 Pollen » avec et sans fertilizer) sont presque identiques pour le joueur.
- **C4. Les événements n'existent ni dans le guide de Sprig, ni dans les règles (`TutorialView`), ni dans GDD/GLOSSARY** : première apparition à la manche 3, sans explication préalable. La prime de 30 Pollen de la manche 1 (« First round bonus ») n'est pas dans les règles non plus.
- **C5. Les engagements (pledges) Minimalist et Lean Bag peuvent être brisés par un événement sans message** : `NotePledgeBroken` n'est appelé que pour Shuffle et Reroll ; une carte « gain a random fertilizer » ou « Joker seed joins your bag » casse Minimalist/Lean Bag sans avertir, et la carte ne le mentionne pas.
- **C6. Guide de Sprig : « Press H for the full rules »** (`GameBootstrap.cs:711`) n'est pas adapté au tactile (aucun clavier sur iPad) ; il faut dire « open Menu > Rules » quand `MobileSetup.IsTouchDevice`. Autres textes non adaptés au tactile : `Loc.cs:19` « Show seed bag (Tab) », `Loc.cs:42` et `SettingsView.cs:168,205` « Click again », `TutorialView.cs:84` « Drag or click ».
- **C7. Un seul retour de sauvegarde « nothing bought yet » à la reprise en boutique** : quitter pendant une boutique rejoue l'événement en attente avec un nouveau tirage (`new SystemRandomProvider()` à la reprise, `RunFlow.cs:671`) ; on peut donc relancer le résultat d'un pari en quittant puis en continuant. Cohérent avec la règle « checkpoint = boutique telle qu'ouverte », mais la contrepartie (rejouer les paris) n'est écrite nulle part. À arbitrer avec l'auteur.
- **C8. Unités : `docs/DECISIONS.md` et `CLAUDE.md` parlent de « 32 graines en manche 2 et 30 en manche 4 »** ; en jeu, Spring a 38 et 36 (base `PieceBudgets` 32/30 + `PieceBudgetBonus` 6). Mesuré : `BudgetFor(1)=38`, `BudgetFor(3)=36` (Spring). Le mot « graines » induit en erreur ; dire « base 32/30 (+6 en Spring) ».

## 4. Cas vérifiés sans écart (pour éviter de les refaire)

- Événements : sac au minimum (10) avec « Burn it » (grisé) et « Dig deep » (« You lose 0 seeds. »), Pollen jamais négatif, 4 fertilizers (Buy a cutting grisé ; Swap OK car perte puis gain), 0 fertilizer (Sell/Swap grisés), `IsEventOptionAvailable == ResolveEvent` dans tous les cas (programme (a), 0 écart), effets « next round » indexés par numéro de manche (expirent seuls, y compris en Endless), jamais d'événement après la dernière manche hors Endless, boutique verrouillée (`BuyBlisterSlot`, `BuyUpgradeSlot`, `RerollShop`, `LeaveShop` refusent tant que `PendingEvent != null`), Orchard/Greenhouse/Autumn (le tirage passe par `IsModifierUsableThisRun`).
- Sauvegarde : aller-retour du checkpoint de boutique avec événement en attente, `seenevents`, `eventseeds`, `eventhp`, Pollen, offres, 6 défis x niveaux 1 et 4, Endless : identique ; reprise puis résolution puis sortie de boutique : OK ; sauvegarde sans clés d'événement : lue ; identifiant d'événement inconnu / de fertilizer inconnu : sauvegarde rejetée proprement (null) et non plantage ; `OnApplicationPause` sauvegarde aussi en AwaitingShop.
- Warden/Aegis/Anchor : l'immunité de Warden est dérivée de la tuile (`GridManager.IsPlotImmune`), tous les effets d'ennemi qui posent verrou/glace/poison passent par ce test (`Locks.cs:47,61,330,385`, `Combat.cs:609,649`) ; `ClearFill` retire la trait d'origine donc la protection disparaît avec la tuile ; Aegis reste pour la manche (`ResetForNewRound`) comme annoncé par son texte et par `DECISIONS.md` (2026-11-20) ; Anchor est exclu de `MovableFilledCells` (recolorer, échanger, déplacer, brûler). Textes des trois sprouts conformes. Une seule amélioration par case (`WithAddedTrait` : « une case que nul autre upgrade n'utilise »), donc `OriginTrait` ne peut pas être écrasé entre deux sprouts.
- Mult arrondi : `ScoreEvent.PreciseAmount` est bien lu par `PlacementResult.Mult` et par la séquence d'affichage (`GameBootstrap.Placement.cs:735`) ; Solidarity est un palier entier voulu (« +1 Mult per 2 fertilizers held », division entière dans le code et dans `RunManager.cs:677`) ; `FormatMultDisplay` arrondit seulement l'affichage (une valeur à moins de 0,05 d'un entier s'affiche entière, par exemple 2,96 s'affiche « 3 »), sans effet sur le score.
- Rythme : le simulateur confirme manche 1 = 9,6 poses (planner), 100 % de réussite ; `EarlyRoundHpFactors` s'applique bien (r1hp = 0,5 x PV de base) ; `LastRoundEndLueurBonus` inclut la prime et le résumé (`RoundSummaryView.cs:137`) la liste sur sa propre ligne ; le décompte animé ne vide que le compteur de graines.

## 5. Invariants proposés pour `Tools/Headless/RunSim/Invariants.cs`

1. À chaque ouverture de boutique, `CheckpointSnapshot` : texte -> `FromText` -> `Restore` -> `CheckpointSnapshot.ToText()` identique, et `PendingEvent` identique (aujourd'hui seul le début de manche est vérifié, `CheckSnapshotRoundTrip`).
2. Après `ResolveEvent` : Pollen >= 0, `DeckCount >= DeckManager.MinDeckSize`, `ActiveModifiers.Count <= 4`, `CurrentBudget >= 1`.
3. `IsEventOptionAvailable(i) == ResolveEvent(i)` (le test de l'effet de bord peut le vérifier sur un clone).
4. `PiecesRemainingThisRound <= CurrentBudget` en début de manche et `CurrentBudget == BudgetFor(round) + delta d'événement`.
5. Faire tourner le fuzz **avec `--events` par défaut** (aujourd'hui `Bot.WithEvents` est faux : les 6 x (100 + 40) parties standard n'ouvrent jamais de carte).
